## 进入研发前必须补齐

### Blocker 1：定义行情数据契约

PRD 只写了“使用 AkShare”，但没有规定每个字段对应的接口、复权方式、单位、交易日和数据截止时间。

至少补充一张“业务字段—接口—源字段—单位—复权—更新时点—缺失降级”映射表，明确：

- 股票池如何覆盖沪、深、北交所，以及 CDR、退市、暂停上市证券如何处理。
- K 线和技术指标使用不复权、前复权还是后复权；价格展示与指标计算是否允许使用不同口径。
- 成交量使用股还是手，成交额使用元还是万元，换手率是小数还是百分数。
- 行业、上市日期、停牌、ST、涨跌停、上涨/下跌家数、北证 50 的具体来源。
- “最新价/今日/当前价”统一定义为“最新已完成交易日收盘数据”，还是允许盘中快照。当前 V1 声称日线级，却在页面中使用了容易被理解为实时行情的文案。
- 同步结果必须保存 `source`、`source_version`、`trade_date`、`fetched_at`、`adjustment` 和完整性状态。

AkShare 官方文档显示，不同历史行情接口的数据来源、字段、单位和限制并不完全一致，并专门维护了数据风险说明。因此不能把“AkShare”当作单一、稳定的数据契约。

### Blocker 2：把指标和信号写成可执行规则

需要给所有规则明确公式、时点和边界：

- `MA5 > MA20` 是状态还是当日上穿事件。
- MACD 金叉定义为 `DIF[t-1] <= DEA[t-1] && DIF[t] > DEA[t]`；死叉反向。
- “红柱放大”比较哪两日，零轴上下是否采用同一规则。
- “近 5 日均量 > 近 20 日均量”是否包含当日、最少样本数、是否要求倍率阈值。
- RSI 50–75 的端点是否包含；从区间外进入才触发，还是每日处于区间都产生事件。
- “放量突破 MA20”中的“突破”必须包含前一日未站上；否则每天站在 MA20 上方都会重复提醒。
- 前高压力位、趋势偏强、风险等级低/中/高目前没有算法，不能直接进入报告。
- 统一规定数值精度、空值、停牌日、除权除息、连续停牌和上市不足 N 日的行为。

建议只有一个 `indicator_engine + signal_engine`，筛选器、提醒和报告读取同一份按 `stock_code + trade_date + rule_version` 生成的结果。

### Blocker 3：补齐同步与事件时序

需要明确一个交易日的状态机：

```text
等待收盘 → 拉取基础行情 → 数据校验 → 计算指标 → 生成信号
→ 更新候选股 → 生成提醒事件 → 看板可见
```

同时定义：

- 初次全量回填多少年；日常增量回补多少个交易日。
- 定时同步具体时间、时区、交易日历来源和手动同步并发策略。
- 失败重试、断点续传、幂等键、部分成功、数据源修订后的重算范围。
- 只有整批数据校验完成后才切换“当前有效批次”，避免用户看到半新半旧的数据。
- 同一规则同一股票同一交易日只产生一个 `alert_event`；确认状态不因重新同步丢失。

## 本轮应完善的 Major 问题

1. **“决策记录”缺失。** 背景和业务流程都承诺记录每日关注结论，但功能清单、页面、数据表和验收标准中没有该能力。建议 V1 要么增加 `decision_note`，要么从目标和流程中删掉。
2. **保存筛选条件缺失。** 埋点和原型存在“保存条件”，详细需求和数据模型没有保存、命名、覆盖、删除、默认方案等规则。建议移到 P1，或补 `screener_preset`。
3. **提醒优先级矛盾。** 自选监控是 P0，提醒规则是 P1，但 P0 看板和自选页依赖提醒结果。建议拆成“内置只读规则与信号计算 P0；规则增删改启停 P1”。
4. **候选股来源不明确。** 应指定一个默认筛选方案、执行时点、排序规则、最大展示数、并列处理和无结果行为。
5. **风险等级无定义。** 建议由负向信号、样本完整度、价格波动等明确规则计算；不要仅按命中信号数量推断。
6. **数据模型不够。** 建议新增 `sync_job`、`daily_indicator`、`signal_event`、`screener_preset`，并为现有表补主键、唯一键、外键、时间字段、状态枚举和规则版本。
7. **报告不可复现。** 报告应保存 `trade_date`、行情批次、指标快照、信号列表、模板版本和生成时间；“重生”应改为“重新生成”，并规定覆盖还是新建版本。
8. **导出没有定义。** 明确格式（建议 V1 仅 Markdown 或 PDF 二选一）、文件名、内容范围和免责声明。
9. **非功能需求缺失。** 至少定义首次同步时长、增量同步时长、筛选响应 P95、详情加载 P95、支持股票数量、失败可恢复性、浏览器范围和备份恢复方式。
10. **部署与访问边界缺失。** 如果仅绑定 `127.0.0.1`，可不做账号系统；若允许局域网或公网访问，必须补认证、HTTPS、CSRF、防暴露配置和密钥管理。
11. **免责声明位置不明确。** 首页、报告页和导出文件固定显示“仅用于个人研究和信息整理，不构成投资建议”；避免目标价、收益承诺和强买卖措辞。
12. **埋点投入偏早。** 单人本地工具可以先用结构化操作日志替代完整埋点系统，把开发资源优先给数据质量、可解释性和可回放性。

## 建议收敛后的 MVP

| 阶段 | 内容 | 验收重点 |
|---|---|---|
| V1.0 | 股票池、交易日历、日线同步、指标计算、股票详情 | 数据口径正确；指标有金样本比对；同步可恢复 |
| V1.1 | 筛选器、默认候选方案、结果排序 | 全市场筛选性能达标；同批数据结果可复现 |
| V1.2 | 自选分组、内置提醒、确认状态 | 事件不重复；重算不破坏确认状态 |
| V1.3 | 规则模板报告、导出 | 报告与详情/筛选信号完全一致；可追溯到数据批次 |
| P1 | 自定义提醒规则、保存筛选条件、参数设置 | 规则版本化；旧事件可解释 |

数据库建议直接确定为 SQLite，适合个人、本地、日线级 V1；只有在明确需要多进程写入、远程部署或多用户时再迁移 PostgreSQL。指标应在同步完成后预计算并缓存，避免每次全市场筛选时临时计算。

## 建议新增的验收标准示例

- 给定固定的 100 只股票、250 个交易日金样本，MA/MACD/RSI/布林带结果与选定基准库逐点比对；容差和舍入方式写入测试说明。
- 同一有效数据批次、同一规则版本重复运行两次，候选股、信号和报告摘要完全一致。
- 同一股票、规则、交易日重复同步，不新增重复提醒事件。
- 某只股票最近 60 个有效交易日不足时，不计算 MA60，页面、筛选和报告均返回统一的“样本不足”。
- 增量同步中途失败后重试，已成功数据不重复写入，旧有效批次仍可查询。
- 全市场默认筛选在目标机器上 P95 小于约定阈值；阈值需由一次技术 Spike 后填写，不建议现在凭空指定。
- 报告中的每条结论都能展开查看公式、输入值、交易日和规则版本。

## 最小技术 Spike（开工前 1～2 天）

1. 用 20 只覆盖沪深京、ST、停牌、次新、除权的样本股验证股票列表、日线、指数、交易日历和必要字段。
2. 固化字段映射、单位、复权方式和降级策略。
3. 对 250 个交易日计算全部指标，记录耗时和与基准库的差异。
4. 将规模扩大到全市场，验证首次同步、增量同步、指标预计算和组合筛选耗时。
5. 根据实测结果填写 PRD 的 SLO，而不是先拍性能数字。
